1. Overview of the Problem

When implementing a GraphSAGE GNN on FPGA, we observed that the HLS implementation output does not match the output produced by the original PyTorch Geometric (PyG) SAGEConv model.

Even after fixing randomness, subgraph extraction, ordering of edge_index, and after improving the Python testbench, the INT8 hardware simulation still differs from the PyG float model.

This mismatch is not caused by bugs in HLS or PyTorch, but by a fundamental architectural difference:

PyG executes the GNN in full float32:

Aggregation in float

Linear layers in float

ReLU in float

Final output is float

Optionally quantized only at the very end

FPGA/HLS executes the GNN in quantized INT8/INT32:

Activations quantized per layer

INT8 × INT8 → INT32 accumulation

Requantize after each layer

Quantization errors accumulate through the network

Numerical domain is totally different from float PyG

This means:
Comparing PyG float against HLS INT8 is meaningless.
They cannot match mathematically.

The mismatch is not a bug.
It is the expected behavior of quantized inference.

2. Why the Mismatch Happens

Even after making the Python testbench perfectly deterministic (fixed seed, fixed center node, fixed edge_index):

PyG performs float aggregation → more dynamic range, no clipping.

HLS performs quantized aggregation → rounding + clipping + scale mismatch.

PyG quantizes only the final output.

HLS quantizes after every operation, many times.

PyG uses float weights.

HLS uses int8 weights.

Requantization scales differ between layers.

Therefore:
the HLS implementation is computing a different numeric function than PyG, even if the graph structure is identical.

This is true for ALL neural networks:

CNNs

Transformers

GNNs

RNNs

etc.

Only quantization-aware training (QAT) produces a model that matches INT math.

3. Possible Solution Paths

There are three practical ways to solve this, depending on your design goals.

-------------------------------------
OPTION A — Avoid quantization for now
-------------------------------------

Use float or wide fixed-point (e.g., ap_fixed<16,6>) in HLS.

Characteristics:

Almost identical to PyG

Very easy to verify and debug

Perfect for a first prototype

Suitable for small graphs (e.g., 8–32 nodes, 16→24→7 dims)

Pros:

Zero accuracy loss

Zero quantization debugging

Simplest HLS implementation

Cons:

Not the final optimized design

Higher DSP and BRAM use

-----------------------------------------------------
OPTION B — Use gentle quantization: int12 or int16
-----------------------------------------------------

Keep:

activations in int12/int16

weights in int16

accumulators in int32

Requantize only per layer.

Pros:

Much smaller quantization error

Still similar to hardware arithmetic

Good transitional approach

Cons:

Not as efficient as full INT8

Still need some calibration

-----------------------------------------------
OPTION C — Full INT8 deployment (production)
-----------------------------------------------

This is the real quantized inference pipeline:

Define a fixed quantization spec

int8 activations

int8 weights

int32 accumulation

per-layer scale s

optional zero-points

Implement a hardware-style quantized GraphSAGE layer in Python

using integer arithmetic, not float

Compare:

HLS ↔ hardware-style Python

NOT HLS ↔ PyG float

Train with QAT (Quantization Aware Training) so that the network learns to work under INT constraints.

Pros:

Truly efficient for large GNNs

DSP-optimal

Industry-standard for inference

Cons:

Longest development cycle

Requires custom Python quantized GraphSAGE

Requires QAT to maintain accuracy

4. Professional Industry Approach

The standard ML-hardware engineering approach (used by Google TPU, NVIDIA, Meta, Xilinx/AAMD DPU) is:

Step 1: Build a float version on hardware

Establish correct dataflow

Verify aggregation primitives

Implement the graph math correctly

Compare exactly against PyG float

Solve bandwidth, pipeline, buffering, scheduling

Step 2: Freeze a quantization spec

Define integer formats

Define requantization math

Define per-layer scales

Write a document describing the exact arithmetic contract

Every tool (PyTorch → testbench → HLS) follows this spec

Step 3: Build a Python “hardware-style” INT8 model

Same quant equations as HLS

Validated against float PyG for accuracy

This becomes the golden reference

Step 4: Do QAT (Quantization Aware Training)

Train the model with fake quantization operators

The model learns to live with INT8 noise

Accuracy becomes hardware-friendly

Step 5: Implement HLS version

Must match the hardware-style Python exactly

Not the float PyG model

Step 6: Hardware verification

Compare output of HLS ↔ hardware-style Python

If they match → deploy

If accuracy drops → fine-tune QAT

5. Recommendation for Your Current Project

Given the size of your prototype GNN (8–32 nodes, 16→24→7 dims) and given that you are still wiring up:

PyG pipeline

Quantization pipeline

Test vector pipeline

HLS pipeline

The most effective approach is:

→ Start with Option A (float / wide fixed)

This removes quantization error as a variable

You can validate graph math, SAGEConv logic, indexing, buffering, pipelining

You can match PyG float outputs exactly

Then:

→ When stable, move to Option C with QAT

6. Final Summary

The mismatch between PyG and HLS INT8 is natural and expected.
It is not a bug in either implementation.

To solve it correctly:

Decide your numeric world.

Build a Python golden reference that uses the same numeric world.

Compare HLS against that golden reference.

Only compare accuracy against PyG float, not values.

This is the professional hardware-ML co-design workflow used by industry accelerators.
